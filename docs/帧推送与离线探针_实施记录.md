### 数据流

```
captureLoop ─capturedFrame{img,captureMs}→ frameQueue(容量1~2,丢最旧)
   → inferLoop → TwoStageDetect
   → Engine.Decide
   → FramePusher.Push ──限流/冻结判定──→ JPEG(≤1280w,q62) + 双坐标框 + ROI
                                        → wailsApp.Event.Emit("sg:frame", payload)
                                        → 前端 RAF 合帧 → 三画布绘制
```

### 关键设计点

1. **有决策的帧强制绕过节流**。否则最想看的瞬间（点击那一刻）会因为刚好落在 450ms 窗口内被丢掉。
2. **双坐标系同时下发**。`box`（屏幕像素）给原屏画布，`box_model`（模型像素）给模型输入画布。前端不做任何坐标换算，避免两套口径。
3. **模型输入画布画的是真正的 letterbox**（含黑边与 pad），每个框旁标注其在模型空间的像素尺寸——这直接回答"这个 × 到底还剩几像素"。
4. **位图按帧缓存复用**。同一帧的屏幕 JPEG 被原屏与模型输入两个画布共用，只解码一次。
5. **事件优先，轮询兜底**。`window.wails.Events.On` 可用时走推送；不可用时退回 500ms 轮询 `GetLiveFrame`，前端初次挂载也先拉一次，避免等下一个事件才出画面。

## 二、本轮修掉的 4 个 bug（全部由 frameprobe 暴露）

按严重程度排序。**这 4 个 bug 在"能编译、能启动、界面正常"的状态下全部不可见。**

### BUG-1（致命）一级容器从未赋 Role，自动点击功能整体失效

```go
// 修复前：一级容器只按类别名筛选，Role 保持零值 ""
realContainers = append(realContainers, b)
```

引擎按 `b.Role == types.RoleContainer` 筛容器 → **永远筛到 0 个** → 所有出口都判 `outside_container` → 一次点击都不会发生。

探针输出 `容器数=0` 时暴露。修复后 `容器数=1`，出口门控 `✓ 通过`。

### BUG-2（致命）动态输入维返回 -1，推理从未成功过

模型输入是 `[batch, 3, height, width]` 符号轴，ORT 的 `GetDimensions` 对动态维返回 **-1 而不是 0**：

```go
if inputW == 0 {        // -1 != 0，回退不触发
    inputW = imgsz
}
// → 拿 -1 去建张量
// 报错：tried creating tensor with negative value in shape
```

修复：C 侧把负维归零，Go 侧判断改为 `<= 0`。

**这个 bug 一直没被发现，是因为 app 从未真正跑过一次推理**（一直卡在无屏幕录制权限、没有帧进队列）。

### BUG-3（严重）第二级误检的容器类泄漏进 Exits

代码注释写着"过滤掉容器类"，实际只改了 `Role` 标签就把全部框 `append` 进 `Exits`。结果同一个弹窗在容器列表里出现两次（一级一个 + 二级误检一个），污染 ROI 排序、弹窗计数与画布显示。

### BUG-4（严重）ORT 错误消息被吞

所有失败分支直接 `return NULL`，丢弃 `OrtStatus`。表现为只有一句"ONNX 推理失败"，无法定位。补 `ortSetErr/ortLastError` 后，BUG-2 的真实原因一眼可见。

> 顺带修正：`GetErrorMessage` 才是 OrtApi 里的正确函数名（不是 `StatusGetMessage`）。

## 三、frameprobe：单帧离线决策模拟器

**这是本轮最有价值的产出**，因为它让整条链路可以在**完全没有屏幕录制权限**的情况下被验证和回归。

```bash
# 基本：看分辨率适配与每个目标在模型空间的实际像素
go run ./cmd/frameprobe -model ../tangchuang/yolo26m.onnx -img shot.png

# 跑完整 9 步决策链，投 4 帧验证点击路径能否真的触发
go run ./cmd/frameprobe -model ... -img shot.png -auto -frames 4

# 模拟用户刚动过鼠标 → 应命中 blocked_user_active
go run ./cmd/frameprobe -model ... -img shot.png -auto -frames 4 -idle 0.5

# 指定 imgsz 做对照实验（这是选档位的正确工具）
go run ./cmd/frameprobe -model ... -img shot.png -imgsz 640
go run ./cmd/frameprobe -model ... -img shot.png -imgsz 1280

# 导出 JPEG / CSV 便于人工核对
go run ./cmd/frameprobe -model ... -img shot.png -out probe_out -csv boxes.csv
```

输出示例（合成弹窗图，1920×1080）：

```
图片      : 1920x1080 px
imgsz     : 1440  (基线公式 0.75×1920 = 1440)
letterbox : ratio=0.7500  newShape=1440x1440  pad=(0.0, 315.0)
检出      : 容器 1 个 / 出口 1 个

类别         conf  屏幕框(宽x高)   模型框(宽x高)   短边px   判定
TanChuang    0.98  526x387        394.5x290.2    290.2    OK
GuanBi       0.91  25x27          19.1x20.0      19.1     OK

决策链模拟（模式=auto, 空闲=999s, 一致性需 4 帧, 本次投 4 帧）：
  逐帧动作 : f1=report_only → f2=report_only → f3=report_only → f4=click
  最终动作 : click
  ✅ 点击路径已打通：容器门控与一致性门控均通过
```

负帧验证（一张正常 macOS 窗口截图，2558×1662，标题栏带 ×）：

```
检出      : 容器 0 个 / 出口 0 个
  最终动作 : report_only
```

**两级调度正确地没有去点标题栏那个 ×** —— 这就是容器约束作为主闸的意义。
