# 权限身份与"多个本体"问题 · 修复记录

日期：2026-09-01

---

## 一、现象

1. 项目根目录同时存在 `screenguard`、`frameprobe` 两个裸二进制和 `ScreenGuard.app`，用户困惑"怎么这么多本体"。
2. 屏幕录制授权后仍"无法识别权限"，交互不稳定。

## 二、根因：两个现象是同一个问题 —— TCC 身份

macOS 的屏幕录制授权（TCC）绑定到**进程的可执行身份**（bundle id + 代码签名 designated requirement）。

实测三个二进制的身份完全不同：

| 二进制 | Identifier | screen-recording entitlement | 能否拿到授权 |
|---|---|---|---|
| 根目录 `screenguard`（裸） | `a.out`（linker-signed） | 无 | ❌ |
| 根目录 `frameprobe`（裸） | `a.out` | 无 | ❌（诊断工具，不需要） |
| `ScreenGuard.app` | `com.screenguard.app` | 有 | ✅ |

- 裸二进制是手动 `go build`（无 `-o`）的残留产物，身份为 `a.out`、无 entitlement。
  用户若双击/运行它，TCC 认的是 `a.out`，而授权给的是 `com.screenguard.app` → **永远"无法识别权限"**。
- 即使是 `.app`，adhoc 签名每次 `make sign` 都会换 CDHash，macOS 可能视其为新应用 → **每次重新构建后需重新授权**。这是"不稳定"的另一半来源。

## 三、修复

### 3.1 清理与防再犯

- 根目录裸二进制 `screenguard`、`frameprobe` 已移入废纸篓。
- `Makefile` 新增 `probe` 目标，`frameprobe` 统一输出到 `build/`；`clean` 会删除根目录残留。
- 启动时若 `paths.BundlePath() == ""`（非 bundle 启动）打印强提示，引导改用 `open ScreenGuard.app`。

### 3.2 权限识别逻辑修正（`internal/app/app.go`）

修复前 `ScreenPermissionState()` 用"像素方差 < 1.0 → needs_restart"做门控。
问题：ScreenCaptureKit 在**未授权**时返回的是**错误**而非壁纸；**已授权**时即使桌面是纯色壁纸也会成功返回图像。
因此方差门控会把"纯色壁纸 + 已授权"误判成未生效，导致授权了仍显示 needs_restart。

修复后：

```
preflight=false            → unauthorized
抓屏返回 error / nil       → needs_restart   （授权了但进程未重启）
抓屏成功（无论壁纸多纯色） → ok
```

### 3.3 授权后重启闭环（`RestartApp`）

新增 `App.RestartApp()`：以 `open -n <bundlePath>` 重新拉起 `ScreenGuard.app`（保证身份是 `com.screenguard.app` 且带 entitlement），再退出旧进程。
前端 OnboardingView 的"重启"按钮改调 `api.restartApp()`，避免用户重启后误开裸二进制。

## 四、稳定性边界（必须向用户说清）

- **adhoc 签名每次重建都会重置授权**。开发期每次 `make sign` 后需重新去系统设置勾选，这是 adhoc 的固有代价。
- **要彻底稳定，必须用 Apple 开发者证书签名**（稳定 TeamIdentifier + designated requirement）。生产环境应上 Developer ID。
- 日常使用只认 `ScreenGuard.app`，不要运行任何裸二进制。

## 五、验证

- `go build ./...` / `go vet` / `npm run build` / `make sign` 全部通过。
- `codesign -dv ScreenGuard.app` → `Identifier=com.screenguard.app`，entitlement 含 screen-recording。
- 根目录不再残留裸二进制。
